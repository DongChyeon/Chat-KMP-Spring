# 02. 로그인 실패 응답으로 새는 계정 정보

- 날짜: 2026-11-08
- 로드맵 단계: 1 (Issue #3)
- 관련 커밋: `b26fe0a`(로그인), `e2c32fb`(수정)

## 예측 (오너 작성)

질문: 로그인 실패를 "가입되지 않은 이메일"과 "비밀번호 틀림"으로 구분해서 응답하면 어떤 문제가 생길까?

> 이메일만 일치하는 것을 확인하면 유출된 비밀번호를 대입해보는 공격도 할 수 있고, 브루트포스 공격을 통해서도 이메일을 먼저 맞추고 비밀번호를 계속 시도해보는 공격을 시도할 수도 있을 것 같아

이 예측에 따라 로그인 실패는 `INVALID_CREDENTIALS` 하나로 응답하도록 구현했다. 응답 **시간**으로도 같은 정보가 샐 수 있다는 점은 예측 단계에서는 다루지 않았다.

## 실행

가입된 이메일 하나를 만들고, 틀린 비밀번호로 두 경우를 20번씩 로그인해 평균 응답 시간을 쟀다.

```bash
./gradlew :server:bootRun
./scripts/login-timing.sh 20
```

- A: 가입되지 않은 이메일
- B: 가입된 이메일 + 틀린 비밀번호

## 관찰

| | A. 없는 이메일 | B. 있는 이메일 | 차이 |
|---|---|---|---|
| 수정 전 | 4.5 ms | 66.6 ms | 약 15배 |
| 수정 후 1회 | 66.7 ms | 64.6 ms | 2.1 ms |
| 수정 후 2회 | 66.0 ms | 65.1 ms | 0.9 ms |
| 수정 후 3회 | 66.5 ms | 66.8 ms | -0.3 ms |
| 최종 코드 (더미 문자열을 UUID로) | 73.1 ms | 70.4 ms | 2.7 ms |

- 두 경우 모두 응답 본문은 `401 INVALID_CREDENTIALS`로 같았다.
- 수정 후의 차이는 몇 ms 안에서 방향이 매번 바뀌었다. 측정 잡음 수준이다.

## 왜

- **예측이 맞은 부분:** 응답 메시지가 다르면 계정 열거로 가입된 이메일을 알아낼 수 있고, 이 목록은 크리덴셜 스터핑이나 표적 무차별 대입에 쓰인다. 그래서 메시지를 하나로 통일했다.
- **예측에 없던 부분:** 메시지를 통일해도 응답 **시간**이 달랐다. 이메일이 없으면 DB 조회 후 바로 실패하고, 이메일이 있으면 BCrypt 비교(일부러 느린 연산)를 한다. 이 차이로 계정 존재 여부를 알아내는 것을 타이밍 공격이라고 한다.
- **고친 방법:** 이메일이 없을 때도 미리 만들어 둔 더미 해시와 BCrypt 비교를 한 번 하게 했다. 두 경우 모두 BCrypt 연산이 정확히 1번씩이 된다.
- **시행착오에서 배운 것:**
  - "비밀번호를 먼저 비교하고 이메일을 나중에 확인"하는 순서는 불가능하다. BCrypt 비교에는 저장된 해시가 필요하고, 해시는 이메일로 사용자를 찾아야 얻을 수 있다.
  - 비교 대신 입력 비밀번호를 매번 `encode()`하면, 있는 이메일 쪽이 BCrypt 2번이 되어 차이가 반대로 생긴다. 더미 해시도 요청마다 만들면 같은 문제가 생긴다. 그래서 서버가 시작될 때 한 번만 만든다.
  - 조건문과 블록 안에서 `matches`를 각각 호출했더니, 없는 이메일 쪽이 BCrypt 2번이 되었다. 시간을 맞추는 코드에서는 연산 횟수를 정확히 세야 한다.
  - 더미 해시는 실제 비밀번호와 **같은 `PasswordEncoder`**로 만들어야 한다. BCrypt 해시에 들어 있는 비용 값(`$2a$10$`의 `10`)이 같아야 비교 시간이 같다.
  - 비교 결과와 **상관없이 무조건** 실패시켜야 한다. `user == null && !matches(...)`처럼 결과에 따라 분기하면, 더미 문자열을 아는 공격자(이 레포는 Public)가 분기를 건너뛰어 다른 응답(500)을 끌어낼 수 있다.
- **남은 과제:** 회원가입 API의 `DUPLICATE_EMAIL` 응답으로도 계정을 열거할 수 있다. 요청 횟수 제한으로 대응할 후속 과제로 Issue #3에 남겼다.

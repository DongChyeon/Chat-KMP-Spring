# 06. unique 제약을 지우면 중복 참여를 코드만으로 막을 수 있나

- 날짜: 2026-11-22
- 로드맵 단계: 2 (부숴보기)
- 관련 결정: ADR 0020(참여자 중간 엔티티), ADR 0021(그룹 방 직접 참여), ADR 0026(`left_at`), ADR 0024(커서)

## 예측 (오너 작성)

질문 1: `(user_id, room_id)` unique 제약을 지운 상태에서 한 사용자가 같은 그룹 방에 참여 요청을 동시에 10개 보내면, 응답은 200 몇 개, 409 몇 개이고 참여 행은 몇 개 생길까?

> 200 응답이 여러개, 그 200 응답만큼 사용자의 행이 생기는 것인데
> 결국 그 여러개의 기준은 ChatRoom 추가가 반영되기 까지 얼마나 많은 동시요청이 들어왔냐 아니야?

질문 2: 참여 행이 여러 개인 사용자가 나가기를 호출하면 어떤 응답이 올까?

> 첫 행의 결과만 leftAt 이 갱신되었다가 null로 바뀌어

## 실행

로컬 DB에서 서버를 띄운 뒤 제약을 지우고 실험한다. 스크립트는 끝나면(실패해도) 중복 행을 지우고 제약을 같은 이름으로 다시 만든다. 서버를 먼저 띄워야 하는 이유는, 나중에 띄우면 `ddl-auto`가 제약을 다시 만들기 때문이다.

```bash
docker compose up -d --wait
./gradlew :server:bootRun
# 다른 터미널에서
./scripts/break-unique-join.sh 10
```

목록이 짧아지는 현상은 같은 방식으로 따로 확인했다. 방 3개에 참여한 사용자를 만들고, 제약을 지운 뒤 가장 최근 방에 SQL로 중복 행 5개를 넣고 `GET /api/rooms?size=2`를 호출했다. 끝난 뒤 복구했다.

## 관찰

**1. 동시 참여 10개**
```
응답 코드: 10 200
guest의 참여 행: 10개 (left_at is null: 10개)
```

**2. 중복 행이 생긴 뒤**
```
내 방 목록 : 200 {"items":[{"id":1011,"type":"GROUP","title":"부숴보기"}],"nextCursor":null}
나가기     : 500 {"code":"INTERNAL_ERROR","message":"서버 오류가 발생했습니다."}
  → guest의 참여 행: 10개 (left_at is null: 10개)
다시 참여  : 500 {"code":"INTERNAL_ERROR","message":"서버 오류가 발생했습니다."}
```
서버 로그:
```
IncorrectResultSizeDataAccessException: Query did not return a unique result: 10 results were returned
```

**3. 목록이 짧아지는 현상**
```
방 3개 생성 후 목록(size=2): items=[1014, 1013], nextCursor="djE6MTAxMw"
가장 최근 방(1014)에 중복 행 5개 추가
같은 SQL을 psql로 직접(limit 3): 1014,1014,1014
API 목록(size=2):          items=[1014],       nextCursor=null
복구 후 목록(size=2):       items=[1014, 1013], nextCursor="djE6MTAxMw"
```

## 왜

질문 1의 예측은 맞았고, 질문 2의 예측은 달랐다.

**1. 1차 방어(조회 후 저장)는 동시 요청을 하나도 막지 못했다.**
10개 요청이 모두 "아직 참여하지 않음"을 조회한 뒤 INSERT까지 갔다. 조회와 INSERT 사이에 다른 요청의 행이 커밋되기 전이라 서로를 보지 못한 것이다. 예측의 "반영되기까지 얼마나 많은 동시 요청이 들어왔냐"가 정확히 이 틈이다. 다만 반영되는 것은 `ChatRoom`이 아니라 참여 행(`ChatRoomMember`)이다. 평소에는 이 틈을 unique 제약이 막는다. 두 번째 INSERT부터 DB가 거부하고, `join()`의 catch가 그 예외를 409로 바꾼다. 제약이 없으니 거부할 주체가 없어서 10개가 모두 200이 됐다.

**2. 나가기는 "첫 행"을 고르지 않고 500으로 실패했다.**
오너의 정리: "findByRoomIdAndUserIdAndLeftAtIsNull은 멤버 하나만 optional로 반환하기로 했는데 여러개여서 애초에 에러가 발생해서 아무것도 갱신되지 않았구나"

반환 타입이 `ChatRoomMember?`(많아야 하나)이므로, Spring Data는 결과가 2개 이상이면 아무거나 고르지 않고 `IncorrectResultSizeDataAccessException`을 던진다. 이 예외는 `ApiException`이 아니어서 `GlobalExceptionHandler`의 마지막 처리(`handleUnexpected`)로 가 500이 되고, 트랜잭션이 롤백돼 아무 행도 바뀌지 않았다. 재참여(`findByRoomIdAndUserId`)도 같은 이유로 500이었다. "한 사람, 한 방, 한 행"이라는 가정은 코드 곳곳에 퍼져 있는데, 그 가정을 실제로 지키는 것은 unique 제약 하나였다.

**3. 목록은 에러 없이 방을 잃어버렸다.**
목록 쿼리는 `size + 1 = 3`행을 가져오는데, DB가 그 3행을 모두 같은 방(1014)의 중복 행으로 채웠다. Hibernate는 같은 엔티티 결과를 하나로 합쳐서 서비스에 1개만 넘겼고, 서비스는 `fetched.size(1) > size(2)`가 거짓이라 "다음 페이지 없음"으로 판단했다. 그래서 1013번, 1012번 방이 목록에서 사라졌다. 응답은 200이었다. 500은 로그와 알림으로 바로 드러나지만, 이 고장은 사용자가 "방이 없어졌다"고 말하기 전까지 아무도 모른다.

**고칠 것인가**
코드는 고치지 않는다. 이 실험은 unique 제약을 지우면 무엇이 깨지는지 보는 것이었고, 제약은 복구했다. 대신 알게 된 것:
- 동시 요청에서 데이터 규칙을 마지막에 지키는 것은 애플리케이션 코드가 아니라 DB 제약이다. 코드의 사전 조회는 친절한 에러를 위한 것이고, 정확성은 제약이 책임진다.
- "결과는 많아야 하나"라는 가정이 깨졌을 때 예외를 던지는 쪽(나가기, 재참여)이, 조용히 합쳐 버리는 쪽(목록)보다 오히려 안전하다.
- 3단계에서 메시지마다 보낼 대상을 찾을 때도 같은 가정에 기댄다. 중복 행이 있으면 같은 사람에게 메시지가 여러 번 갈 수 있다.

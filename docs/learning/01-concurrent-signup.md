# 01. 같은 이메일로 동시 회원가입

- 날짜: 2026-11-08
- 로드맵 단계: 1 (Issue #3)
- 관련 커밋: `a300a8b`(회원가입), `46154dd`(수정)

## 예측 (오너 작성)

질문: `email`에 UNIQUE 제약 없이 코드에서만 "조회 후 저장"하면, 같은 이메일로 가입 요청 두 개가 동시에 들어올 때 무슨 일이 생길까?

> 같은 이메일로 중복 회원가입이 발생하는 거 아니야?

## 실행

`email`에 UNIQUE 제약을 건 상태에서, 같은 이메일로 회원가입 요청 20개를 동시에 보냈다.

```bash
./gradlew :server:bootRun
./scripts/race-signup.sh 20
```

## 관찰

| 응답 | 수정 전 | 수정 후 (3회 반복, 모두 같음) |
|---|---|---|
| 201 가입 성공 | 1 | 1 |
| 409 `DUPLICATE_EMAIL` | 10 | 19 |
| 500 `INTERNAL_ERROR` | 9 | 0 |
| DB에 저장된 계정 | 1 | 1 |

- 수정 전: 500이 난 요청의 서버 로그에 `DataIntegrityViolationException`(UNIQUE 제약 위반)이 찍혔다.
- 수정 후: 서버 로그에 ERROR가 하나도 없었다.

## 왜

- **예측과 달랐던 점:** 중복 계정은 생기지 않았다. UNIQUE 제약이 있어서 DB가 두 번째 INSERT를 거절했다. 예측한 "중복 가입"은 UNIQUE 제약이 **없을 때** 일어나는 일이고, 제약이 있으면 대신 **에러 응답**이 문제가 된다.
- **500이 난 이유:** 여러 요청이 `existsByEmail` 확인을 동시에 통과했다. 조회와 저장 사이에 틈이 있기 때문이다. 이 요청들이 `save()`에서 제약 위반 예외를 맞았는데, 이 예외를 처리하는 코드가 없어서 500으로 응답됐다.
- **고친 방법:** `save()`를 `try`로 감싸 `DataIntegrityViolationException`을 409 `DUPLICATE_EMAIL`로 바꿨다.
- **`try`가 동작하는 이유:** JPA는 보통 INSERT를 트랜잭션 커밋까지 미룬다(쓰기 지연). 하지만 ID 생성 전략이 `IDENTITY`이면 DB가 INSERT하면서 ID를 만들기 때문에, `save()`를 호출하는 순간 INSERT가 실행된다. 그래서 예외가 `try` 블록 안에서 터진다.
- **주의할 점:** ID 생성 전략을 `SEQUENCE`로 바꾸면 INSERT가 커밋 시점으로 밀려서, 이 `try`가 예외를 잡지 못하고 다시 500이 난다.
- **배운 것:** 코드에서 하는 확인(1차 방어)만으로는 동시 요청을 막을 수 없다. 최종 방어선은 DB 제약이다. 이 "조회와 저장 사이의 틈"은 4단계(안 읽은 수)에서 다시 나온다.

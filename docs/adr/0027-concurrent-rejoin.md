# 0027. 동시 재참여: 별도 동시성 제어를 두지 않는다

- 상태: 채택
- 날짜: 2026-11-21
- 로드맵 단계: 2
- Issue: #7

## 맥락

ADR 0026에 따라 나간 사람의 참여 행은 지우지 않고 `left_at`만 남긴다. 그래서 그룹 방 재참여는 새 행 INSERT가 아니라 기존 행의 `left_at`을 비우는 UPDATE다.

처음 참여할 때는 동시 요청이 들어와도 `(user_id, room_id)` unique 제약이 두 번째 INSERT부터 거부한다. 그래서 200 1개, 409 9개가 보장된다. UPDATE는 행 수도, `(user_id, room_id)`도 바꾸지 않으므로 unique 제약이 끼어들지 않는다.

재현 테스트에서 나갔던 사용자가 재참여 요청을 동시에 10개 보냈을 때 200이 6~7개 나왔고, 개수는 실행할 때마다 달랐다. 최종 상태(참여 행 하나, 참여 중)는 항상 올바랐다.

## 선택지

결정은 두 축으로 나뉜다.

**축 1. 이미 참여 중일 때의 응답**
- 409: 이미 참여한 방이라고 알린다. 처음 참여와 같은 정책이다.
- 200: 이미 참여 중이어도 성공으로 본다(멱등). 앱이 재시도해도 에러 처리가 필요 없다.

**축 2. 재참여 전이의 동시성**
- A. 그대로 둔다: 변경이 없고 대기도 없다. 전이가 여러 번 실행될 수 있어, 3단계에서 입장 메시지 같은 부수 효과가 붙으면 여러 번 실행된다.
- B. 비관적 락(`SELECT ... FOR UPDATE`): 전이가 정확히 한 번이다. 잠금을 기다리는 동안 커넥션을 붙잡는다.
- C. 낙관적 락(`@Version`): 대기가 없다. 컬럼이 늘고, 충돌 예외를 응답으로 바꿔야 한다.
- D. 조건부 UPDATE(`WHERE left_at IS NOT NULL`, 바뀐 행 수로 판단): 쿼리 하나로 원자적이다. `@Modifying` 쿼리를 직접 쓰고, 영속성 컨텍스트와 DB 값이 어긋날 수 있다.

축 1(응답 정책)은 앱과의 약속이고, 축 2(동시성)는 서버 내부의 정확성이다. 응답을 200으로 통일해도 부수 효과의 중복은 막지 못한다.

## 결정

- 축 1: 이미 참여 중이면 409를 유지한다.
- 축 2: A. 재참여 전이에 별도 동시성 제어를 두지 않는다. 동시 재참여에서 200이 하나라는 보장은 없다.

## 이유 (오너 작성)

처음 답:

> 딱히 실패 비용도 크지 않고 동시 요청이 많을 때 대기를 줄이기 위해 A를 택하되 일관성을 위해 이미 참여 중이어도 200 응답을 적용할게. 나중에 입장 메시지를 넣는다고 하면 서버의 응답 코드가 갈린다면 둘 다 분기처리를 동일하게 해야 하기 떄문이야.

되물음: 3단계에서 재참여에 성공하면 입장 메시지를 보낸다고 할 때, 동시 재참여 10개가 들어오면 owner의 화면에는 입장 메시지가 몇 번 보이고, 앱의 분기 처리로 막을 수 있나?

> owner에 입장에서는 10번 보이겠네... 막을 수 없겠다

응답 정책(축 1)과 동시성(축 2)이 독립적인 결정이라는 점을 짚은 뒤:

> 200 으로 통일하든 안하든 입장 메시지가 여러번 발생할 수 있다는 것은 동일하다면 200으로 맞출 이유가 있어?

> 만약 중복 호출한다면 이미 참여한 방입니다 라고 보내는 것도 좋은 것 같아. 그러면 지금 형태 유지할게

되물음: 지금 형태 그대로 동시 재참여 10개를 보낸 재현 결과에서 409와 200은 각각 몇 개였고, 목표와 맞나?

> 실제로 동시에 발생하는 요청이 적을 뿐만 아니라 굳이 정확성이 필요한 것은 아닐 것 같아.
> 200 갯수가 하나임이 보장안된다는 사실은 알고 있어

## 결과

- `join()`은 바꾸지 않는다. 재참여 경로에는 unique 제약 같은 마지막 보루가 없다.
- 테스트 `나갔던 사용자가 동시에 여러 번 재참여하면 200이 여러 개일 수 있지만 결국 참여 중이다`는 200 개수가 아니라 최종 상태만 검증한다.
- 3단계에서 재참여에 부수 효과(입장 메시지 등)를 붙일 때 이 결정을 다시 검토한다. 그때는 축 2를 B~D 중 하나로 바꿔야 부수 효과가 한 번만 실행된다.

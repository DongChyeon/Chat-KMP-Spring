# 0037. 메시지 순서: 전역 id(자동 증가 PK)

- 상태: 채택
- 날짜: 2026-11-22
- 로드맵 단계: 3
- Issue: #9

## 맥락

같은 방에서 거의 동시에 보낸 메시지를 모든 참여자가 같은 순서로 보려면 정렬 기준이 필요하다. 이 기준은 메시지 이력 조회의 커서이자 재연결 복구("마지막으로 받은 것 이후")의 기준이 된다.

## 선택지

### A. 전역 id
메시지 테이블의 자동 증가 PK(`identity`).
- 장점: 따로 구현할 것이 없다. 채팅방 목록처럼 id 커서를 그대로 쓴다(ADR 0024).
- 단점: id는 insert할 때 정해지지만, 다른 트랜잭션에는 커밋한 뒤에야 보인다. 그래서 작은 id가 큰 id보다 늦게 커밋될 수 있고, 그 사이에 "큰 id 이후"를 요청하면 작은 id를 영영 건너뛴다. 여러 방이 번호를 나눠 쓰므로 한 방 안에서는 번호가 띄엄띄엄이라 빈칸을 알아챌 수 없다.

### B. 방별 시퀀스 번호
방마다 1, 2, 3… 연속 번호. 저장할 때 방의 마지막 번호를 잠그고 +1 한다.
- 장점: 한 방 안에서 번호가 연속이라 빈칸을 바로 안다. 번호를 매기는 순서와 커밋 순서가 같아서 복구할 때 건너뛰지 않는다.
- 단점: 같은 방의 저장이 그 방의 행 잠금을 두고 줄을 선다. 컬럼과 잠금을 직접 구현해야 한다.

### C. 시각(`created_at`)
- 장점: 사람이 보는 보낸 시각과 정렬이 일치한다.
- 단점: 같은 밀리초면 보조 기준이 필요하다. 시각도 커밋 전에 찍히므로 A와 같은 건너뜀 문제가 있다. 서버가 여러 대면 서버마다 시계가 다르다.

## 결정

A를 선택한다.

## 이유 (오너 작성)

> 가장 간단한 방법인 A안을 채택하고 이후의 복구 수단은 추가로 고민할게

## 재현 (2026-11-22, 로컬 PostgreSQL 18)

임시 테이블에서 두 트랜잭션을 겹쳐 실행했다.

```
[t=0s] T1 insert -> id 1 (아직 커밋 전)
[t=1s] T2 insert+commit -> id 2
[t=2s] C가 재연결하며 복구: lastSeen=0 이후 요청
  받음: id=2 B의 메시지
  -> C는 lastSeen=2 로 저장
[t=3s] T1 commit
[t=4s] C가 다음 복구: lastSeen=2 이후 요청
  0건
[t=4s] 실제 DB 내용
  id=1 A의 메시지
  id=2 B의 메시지
```

## 결과

- 메시지 PK는 `identity`로 자동 증가한다. 방 안의 순서는 `id` 오름차순이고, 이력 조회 커서도 `id`다.
- 전달 프레임과 이력 응답에 이 id를 싣는다(ADR 0035).
- 위 재현처럼 "X 이후" 방식의 이어받기 복구에서는 메시지를 건너뛸 수 있다. 이 보정은 재연결 복구 결정에서 다룬다. 방에 들어갈 때 최신 N개를 불러오는 조회에는 영향이 없다.
- 한 방 안에서 번호가 연속이 아니므로, 클라이언트는 받은 id만 보고 빈칸을 알아챌 수 없다(ADR 0036의 연결 중 유실도 마찬가지).

# 0020. 사용자와 채팅방의 N:M 매핑: 중간 엔티티(ChatRoomMember)

- 상태: 채택
- 날짜: 2026-11-10
- 로드맵 단계: 2
- Issue: #7

## 맥락

사용자와 채팅방은 N:M 관계라서 DB에는 `(user_id, room_id)` 쌍을 저장하는 중간 테이블이 생긴다. 이 테이블을 JPA 코드에서 어떻게 다룰지 정해야 한다. 4단계(읽음 표시, 안 읽은 수)에서는 참여자마다 "어디까지 읽었나"를 저장해야 할 수 있다.

## 선택지

### A. `@ManyToMany`
- 장점: 코드가 가장 짧다. 중간 테이블용 엔티티와 리포지토리가 없다.
- 단점: 중간 테이블에 다른 컬럼(참여 시각, 방장 여부, 읽은 위치)을 넣을 수 없다. 컬렉션을 바꿀 때 나가는 SQL을 직접 정할 수 없다.

### B. 중간 엔티티 (`ChatRoomMember`, `@ManyToOne` 2개)
- 장점: 참여 정보를 컬럼으로 자유롭게 추가할 수 있다. unique 제약과 인덱스를 직접 건다. 중간 테이블을 직접 조회할 수 있다.
- 단점: 엔티티와 리포지토리가 늘어난다. 방에서 사용자로 가려면 한 단계를 더 거친다. 연관관계를 따라가는 지점마다 N+1이 생길 수 있다.

### C. 중간 엔티티 + id만 저장 (엔티티 참조 없음)
- 장점: 지연 로딩이 없어 연관관계로 인한 N+1이 없다. 나가는 쿼리를 예측하기 쉽다.
- 단점: 연관된 객체를 따라갈 수 없어 조인이나 추가 조회를 직접 써야 한다. JPA의 객체 탐색 장점을 대부분 포기한다.

## 결정

B를 선택한다.

## 이유 (오너 작성)

> 중간 엔티티의 컬럼 자유성을 챙김과 동시에 JPA의 객체 탐색 장점을 어느정도 가져가기 위함이야. 구현하면서 발생하는 N+1 쿼리는 이슈에 적은대로 실무에서도 빈번히 발생하는 이슈이니 직접 해결해볼게

## 결과

- `chat_room_members` 테이블에 `user_id`, `room_id`와 참여 정보 컬럼을 둔다. `(user_id, room_id)`에 unique 제약을 건다.
- 목록 조회처럼 여러 방이나 참여자를 한꺼번에 불러오는 곳에서는 SQL 로그로 N+1을 확인하고 해결한다(Issue #7 작업 목록).

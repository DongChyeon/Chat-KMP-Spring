# 0041. 입장/퇴장 안내: messages에 저장하는 시스템 메시지

- 상태: 채택
- 날짜: 2026-11-23
- 로드맵 단계: 3
- Issue: #9

## 맥락

그룹 방에 누가 들어오고 나갔는지 방 안의 사람들에게 알릴지 정한다. ADR 0027은 동시 재참여에서 200이 여러 번 나갈 수 있게 두었고, 재참여에 부수 효과가 붙으면 다시 검토한다고 적었다.

## 선택지

### A. 이번 단계에서는 없음
참여와 퇴장은 REST 응답과 참여자 목록에만 반영한다.
- 장점: 추가 작업이 없다. ADR 0027을 다시 볼 필요가 없다.
- 단점: 방 안의 사람들은 참여자 목록을 다시 불러와야 변화를 안다.

### B. 메시지로 저장하는 시스템 메시지
`messages`에 종류 컬럼(`TEXT`/`SYSTEM`)을 두고, 입장/퇴장을 한 행으로 저장해 일반 메시지처럼 전달한다.
- 장점: 이력에 남아 나중에 들어온 사람도 본다. 순서, 복구, 목록 정렬을 일반 메시지와 똑같이 처리한다.
- 단점: ADR 0038 스키마를 고쳐야 한다. ADR 0027 그대로라면 동시 재참여 때 입장 메시지가 여러 개 저장되어 영구히 남는다.

### C. 저장하지 않는 실시간 이벤트
`MEMBER_JOINED`/`MEMBER_LEFT` 프레임만 방의 연결들로 보낸다.
- 장점: 스키마를 바꾸지 않는다. 중복이 와도 상태 이벤트라 앱에서 무시하기 쉽다.
- 단점: 이력에 남지 않아 그때 연결이 없던 사람은 모른다.

## 결정

B를 선택한다.

## 이유 (오너 작성)

> B를 고를게. 입장/퇴장 메시지를 나중에 들어온 사람도 조회할 수 있도록 하기 위함이야

B의 단점을 묻는 질문("ADR 0027 그대로 동시 재참여 요청이 3번 오면 입장 메시지는 몇 줄 남나? 받아들일까, ADR 0027을 다시 볼까?")에 대한 답:

> 3줄 남을거야. ADR 0027을 다시보자

(정확히는 최대 3줄이고, 실행할 때마다 1~3줄로 달라진다. ADR 0027의 재현에서 동시 10개 중 200이 6~7개였다.)

## 결과

- ADR 0038의 `messages`에 종류 컬럼(`TEXT`/`SYSTEM`)을 추가한다. 시스템 메시지의 `sender_id`는 입장/퇴장한 당사자로 두고, 문구는 저장하지 않고 앱이 종류와 당사자로 만든다. 세부 형식은 구현할 때 정한다.
- 시스템 메시지는 참여/퇴장을 처리하는 트랜잭션 안에서 저장하고, 커밋한 뒤 전달한다(ADR 0035). `chat_rooms.last_message_id`도 일반 메시지처럼 갱신한다(ADR 0040).
- 처음 참여는 unique 제약이 두 번째 INSERT를 거부하고 그 트랜잭션이 롤백되므로, 입장 메시지도 하나만 남는다.
- 재참여(UPDATE)와 퇴장은 unique 제약의 보호를 받지 않는다. 이 둘을 한 번만 실행하는 방법은 ADR 0027을 다시 검토해서 정한다.

# 0012. Refresh Token 형태와 JWT 서명 방식: JWT, HS256

- 상태: 채택
- 날짜: 2026-11-08
- 로드맵 단계: 1
- Issue: #3

## 맥락

토큰 발급을 구현하기 전에 Refresh Token의 형태와 Access Token(JWT)의 서명 방식을 정해야 한다. Refresh Token은 ADR 0010에 따라 DB(허용 목록)에서 조회한다.

## 선택지

### Refresh Token 형태
- **무작위 문자열 (opaque)**: 단순하고, 탈취돼도 안에서 읽을 정보가 없다. 유효한지는 DB 조회로만 알 수 있다.
- **JWT**: 서명과 만료 시간을 담고 있어서, DB를 조회하기 전에 만료되거나 위조된 토큰을 먼저 걸러낼 수 있다. DB 조회와 역할이 일부 겹치고 토큰이 길어진다.

### 서명 방식
- **HS256**: 비밀키 하나로 서명하고 검증한다. 단순하지만 검증하는 모든 서버가 비밀키를 가져야 한다.
- **RS256**: 개인키로 서명하고 공개키로 검증한다. 다른 서비스가 토큰을 검증해야 할 때 유리하지만 키 쌍 관리가 필요하다.

## 결정

- Refresh Token도 JWT로 발급한다.
- 서명은 HS256으로 한다.

## 이유 (오너 작성)

> Refresh Token: 만료나 위조를 먼저 판독하기 위해서야

> 서명 방식: 현재는 HS256 방식으로도 충분할 것 같으니 나중에 다른 서비스까지 확장되면 RS256 방식을 채택하도록 할게

## 결과

- 채팅 요청마다 DB 조회를 줄이는 효과는 Access Token이 JWT라서 생긴다(ADR 0005). Refresh Token은 재발급할 때만 서버로 오므로 형태가 채팅 요청 비용에 영향을 주지 않는다. (결정 과정에서 확인한 사실)
- Access Token과 Refresh Token을 같은 비밀키로 서명하므로, 토큰에 종류(`type`) 클레임을 넣고 검증할 때 반드시 확인한다. 확인하지 않으면 Refresh Token을 Access Token처럼 쓸 수 있다.
- 비밀키는 환경 변수 `JWT_SECRET`으로 주입한다. 서버가 여러 대가 되면 모든 서버가 같은 값을 써야 한다.
- 다른 서비스가 토큰을 검증해야 하는 시점이 오면 RS256으로 바꾼다.

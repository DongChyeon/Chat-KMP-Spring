# 0024. 페이지네이션: 불투명 커서

- 상태: 채택
- 날짜: 2026-11-10
- 로드맵 단계: 2
- Issue: #7

## 맥락

내 채팅방 목록과 공개 방 탐색 목록을 페이지 단위로 내려줘야 한다. 정렬은 방 id 내림차순으로 시작하고, 3단계에서 최근 메시지순으로 바꾼다(ADR 0023). 앱은 무한 스크롤로 목록을 보여준다.

## 선택지

### A. offset (`?page=2&size=20`)
- 장점: 구현이 가장 단순하다(Spring Data `Pageable`). 페이지 번호 이동과 전체 개수를 줄 수 있다. 정렬이 바뀌어도 API 형태는 그대로다.
- 단점: 뒤 페이지로 갈수록 앞의 행을 읽고 버려서 느려진다. 페이지 사이에 방이 생기거나 빠지면 중복이나 누락이 생기고, 최근 메시지순에서는 더 자주 생긴다.

### B. id 커서 (`?cursor=153`)
- 장점: 페이지 깊이와 관계없이 속도가 같다. 방이 생기거나 빠져도 중복과 누락이 없다.
- 단점: 페이지 이동과 전체 개수가 없다. 정렬 기준이 바뀌면 커서 의미가 달라져 API를 바꿔야 한다.

### C. 불투명 커서 (서버만 해석하는 문자열에 `(정렬값, id)`를 담음)
- 장점: B의 장점에 더해, 정렬 기준이 바뀌어도 API 형태와 앱 코드가 그대로다.
- 단점: 인코딩과 디코딩, 조건 쿼리를 직접 만든다. 잘못되거나 조작된 커서를 처리해야 한다. 지금은 정렬값이 id 하나라 미리 하는 설계다.

## 결정

C를 선택한다.

## 이유 (오너 작성)

> 최근 메시지 순을 적용할 때의 API 미변경, 그리고 offset이 큰 페이지의 성능 저하를 방지하고, 도중에 리스트가 변경되더라도 누락되거나 중복되는 항목이 없도록 C를 채택할게. 구현에서 오는 복잡도는 감수할게

## 결과

- 요청은 `?cursor=...&size=...`이고, 첫 페이지는 `cursor`를 생략한다. 응답은 `items`와 `nextCursor`이며, 마지막 페이지면 `nextCursor`가 `null`이다.
- 다음 페이지가 있는지는 `size + 1`개를 조회해서 판단한다. 전체 개수와 페이지 번호 이동은 제공하지 않는다.
- 해석할 수 없는 커서는 400으로 응답한다.
- 3단계에서는 커서 안의 값만 `(마지막 메시지 시각, id)`로 바꾼다. 스크롤 중에 정렬값이 바뀐 방을 어떻게 다룰지는 그때 다시 결정한다(ADR 0023).

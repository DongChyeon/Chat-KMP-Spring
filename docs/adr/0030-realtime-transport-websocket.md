# 0030. 실시간 전송: 순수 WebSocket

- 상태: 채택
- 날짜: 2026-11-22
- 로드맵 단계: 3
- Issue: #9

## 맥락

3단계에서 메시지를 실시간으로 주고받아야 한다. 인증, 메시지를 보내는 경로, 순서 보장 같은 나머지 결정이 모두 전송 방식에 따라 달라지므로 이것을 먼저 정한다. 서버는 1대로 가정하고, 서버 간 전달은 7단계에서 다룬다.

## 선택지

### A. 순수 WebSocket
연결 하나로 양방향 텍스트 프레임을 주고받는다. 메시지 형식(종류, 방 id 등)과 라우팅은 직접 정의한다.
- 장점: 연결 관리(세션 보관, 방 구독, 끊김 처리)가 코드에 그대로 드러난다. 의존성이 적다. KMP 앱은 Ktor 클라이언트의 WebSocket으로 바로 붙는다.
- 단점: 방 구독, 메시지 종류 구분, 핑/퐁, 에러 프레임을 직접 설계하고 구현해야 한다.

### B. STOMP over WebSocket
WebSocket 위에 STOMP(`SUBSCRIBE`, `SEND`, destination)를 얹고 Spring의 메시지 브로커 기능을 쓴다.
- 장점: 방 구독, 목적지 라우팅, 인증 인터셉터를 Spring이 제공한다. 7단계에서 외부 브로커(Redis, RabbitMQ)로 옮기는 경로가 정해져 있다. Spring 실무에서 많이 쓴다.
- 단점: 연결 관리와 라우팅이 프레임워크에 감춰진다. KMP용 STOMP 클라이언트 선택지가 적다.

### C. SSE + REST 전송
서버 → 앱은 SSE, 앱 → 서버는 REST `POST`.
- 장점: 일반 HTTP라서 기존 JWT 필터, 프록시, 로드밸런서와 잘 맞는다. 구현이 가장 단순하다.
- 단점: 단방향이라 앱 → 서버 실시간 신호도 REST로 보내야 한다. 연결 관리로 배울 거리가 적다. 메신저 실무에서는 WebSocket보다 덜 쓰인다.

## 결정

A를 선택한다.

## 이유 (오너 작성)

> A로 갈게. STOMP 로 처음 시작하면 상당 부분이 추상화되어 있기 때문에 직접 구현하면서 연결 관리를 직접 구현해보기 위함이야

## 결과

- Spring의 WebSocket 지원(`WebSocketHandler`)으로 엔드포인트 하나를 연다. 메시지 브로커와 STOMP는 쓰지 않는다.
- 프레임 형식(종류 구분 필드, 방 구독/해제, 에러 프레임)은 `shared`에 직접 정의한다. 형식 세부는 다음 결정들(인증, 보내는 경로, 순서 보장)과 함께 정한다.
- 연결된 세션과 방 구독 정보는 서버 메모리에 보관한다. 서버가 1대라는 가정에 기대는 부분이며, 7단계에서 서버 간 전달을 설계할 때 이 구조를 다시 본다.
- 연결이 살아 있는지 확인하는 방법(핑/퐁, 타임아웃)도 직접 정한다.

# 0021. 그룹 방 참여 방식: 공개 방 직접 참여로 시작하고 초대로 고도화한다

- 상태: 채택
- 날짜: 2026-11-10
- 로드맵 단계: 2
- Issue: #7

## 맥락

`GROUP` 방(ADR 0019)에 사용자가 어떻게 들어오는지 정해야 한다. `DIRECT` 방은 만들 때 상대가 정해지므로 이 결정과 관계없다.

## 선택지

### A. 초대 (참여자가 다른 사용자를 추가)
- 장점: 모르는 사람이 들어올 수 없다. 상대 지정 방식을 `DIRECT` 방 생성과 같이 쓴다.
- 단점: 초대 권한 규칙이 필요하다. 초대받는 사람의 동의 없이 추가된다. 여러 명 중 일부가 이미 참여 중일 때의 처리를 정해야 한다.

### B. 공개 방 (누구나 목록에서 찾아 직접 참여)
- 장점: 참여 API가 `roomId` 하나로 단순하다. 동시 참여가 자연스럽게 생긴다.
- 단점: "공개 방 탐색 목록" API가 하나 더 필요하다(커서 페이지네이션 두 벌). 비공개 그룹 대화를 할 수 없다.

### C. 초대 코드
- 장점: 사용자를 검색하거나 지정할 필요가 없다. 앱 밖으로 공유할 수 있다.
- 단점: 코드 생성, 추측 방지, 만료, 재발급을 관리해야 한다. 유출되면 누구나 들어온다.

## 결정

이번 단계에서는 B로 구현하고, 이후 A로 고도화한다.

## 이유 (오너 작성)

> B로 먼저 간단하게 구현할게. 그리고 A로 고도화하면서 생기는 문제를 대응하도록 할게

되물음: B도 "공개 방 탐색 목록" API가 하나 더 필요한데 그래도 A보다 간단하다고 본 이유는? A를 붙일 때 이미 만들어진 공개 방은 어떻게 되나?

> 누구나 참여 가능한 상황에서 이제 초대 권한 규칙을 추가로 초대하고 초대할 때 이미 참여 중이면 중복 초대가 가지 않도록 해야해.
> 이미 만들어진 공개방은 참여가 불가능하고 초대 권한이 있는 사람의 초대로만 참여가 가능해

## 결과

- 이번 단계: `GROUP` 방은 모두 공개 방이다. 공개 방 탐색 목록 API와 참여 API(`roomId`)를 만든다.
- A로 고도화할 때: 초대 권한 규칙과 중복 초대 방지를 추가한다. 기존 공개 방도 직접 참여를 막고 초대로만 들어오게 한다. 그러면 공개 방 탐색 목록 API와 직접 참여 API는 쓰이지 않게 되므로, 이 두 API는 앱과 함께 정리해야 한다.
- 고도화는 별도 Issue로 진행한다.

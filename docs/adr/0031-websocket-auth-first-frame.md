# 0031. WebSocket 인증: 연결 후 첫 프레임으로 토큰 전달

- 상태: 채택
- 날짜: 2026-11-22
- 로드맵 단계: 3
- Issue: #9

## 맥락

ADR 0030에 따라 순수 WebSocket을 쓴다. WebSocket은 HTTP 요청 하나(핸드셰이크)로 시작해서 연결을 업그레이드하고, 그 뒤로는 HTTP가 아니다. 그래서 요청마다 `Authorization` 헤더를 읽는 기존 JWT 필터(`JwtAuthenticationFilter`, ADR 0005)가 연결 이후에는 적용되지 않는다. "이 연결이 누구의 것인지"를 언제, 어디서 확인할지 정해야 한다.

연결 중 Access Token이 만료되는 경우는 이 결정에 따라 달라지므로 다음 결정에서 따로 다룬다.

## 선택지

### A. 핸드셰이크의 `Authorization` 헤더
업그레이드 요청에 지금처럼 `Bearer` 토큰을 담는다.
- 장점: 업그레이드 요청도 HTTP라서 기존 JWT 필터와 Security 설정을 그대로 쓴다. 인증에 실패하면 연결 자체가 열리지 않는다.
- 단점: 브라우저의 JS `WebSocket` API는 헤더를 붙일 수 없다. 지금 클라이언트(Android/iOS)는 문제없지만 웹 클라이언트가 생기면 다른 방법이 필요하다.

### B. 핸드셰이크의 쿼리 파라미터
`ws://…/ws?token=…`
- 장점: 브라우저를 포함한 모든 클라이언트에서 동작한다. 연결 전에 인증한다.
- 단점: 토큰이 URL에 들어가 서버 접근 로그, 프록시 로그에 남을 수 있다. 기존 필터는 헤더만 읽으므로 따로 처리해야 한다.

### C. 연결 후 첫 프레임으로 인증
연결을 먼저 열고, 첫 프레임 `{"type":"AUTH","token":"…"}`로 인증한다. 정해진 시간 안에 오지 않으면 서버가 끊는다.
- 장점: 모든 클라이언트에서 동작하고 토큰이 URL에 남지 않는다. 같은 방식으로 연결 중 재인증도 할 수 있다.
- 단점: 잠깐이지만 인증되지 않은 연결이 서버 자원을 차지한다. 인증 전 상태, 타임아웃, 인증 전에 온 다른 프레임의 처리를 직접 구현해야 한다.

## 결정

C를 선택한다.

## 이유 (오너 작성)

> 나중에 웹 확장성을 고려하고, 토큰이 URL을 통해서 노출되는 것을 방지 하기 위해 C 안을 선택할게

## 결과

- WebSocket 엔드포인트(핸드셰이크)는 Security에서 인증 없이 열어 둔다. 인증은 핸드셰이크가 아니라 `WebSocketHandler` 안에서 한다.
- 연결마다 "인증 전 / 인증됨" 상태를 둔다. 인증 전에는 `AUTH` 프레임만 받고, 다른 프레임이 오면 에러를 보내고 끊는다.
- 연결 후 일정 시간 안에 `AUTH`가 오지 않거나 토큰 검증에 실패하면 서버가 연결을 닫는다. 시간 값과 닫을 때 쓰는 close code는 구현에서 정한다.
- 토큰 검증은 기존 `JwtProvider`를 재사용한다. HTTP 필터처럼 DB 조회는 하지 않는다.
- `AUTH` 프레임과 인증 결과 프레임은 `shared`의 프로토콜 정의에 넣는다.
- 인증되지 않은 연결이 자원을 차지하는 문제(연결만 열고 인증하지 않는 클라이언트)는 타임아웃으로 줄인다. 연결 수 제한 같은 추가 방어는 지금은 하지 않는다.

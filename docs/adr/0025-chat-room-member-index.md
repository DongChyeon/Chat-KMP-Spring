# 0025. 참여자 테이블 인덱스: (user_id, room_id) unique + (room_id)

- 상태: 채택
- 날짜: 2026-11-10
- 로드맵 단계: 2
- Issue: #7

## 맥락

`chat_room_members`(ADR 0020)에 나가는 주요 쿼리는 셋이다.

1. 내 방 목록: `WHERE user_id = ? AND room_id < 커서 ORDER BY room_id DESC` (ADR 0023, 0024). 앱을 열 때마다 호출된다.
2. 방의 참여자 조회: `WHERE room_id = ?`. 나가기와 1:1 방 찾기에서 쓰고, 3단계에서는 메시지마다 보낼 대상을 찾는 데 쓴다.
3. 중복 참여 방지: `(user_id, room_id)` unique 제약.

복합 인덱스는 왼쪽 컬럼부터 쓸 수 있다.

## 선택지

### A. `(user_id, room_id)` unique 하나만
- 장점: unique 제약이 1의 인덱스를 겸한다. 정렬도 인덱스 순서 그대로다. 쓰기 비용이 가장 적다.
- 단점: 2는 이 인덱스를 쓰지 못해 테이블 전체를 훑는다.

### B. `(room_id, user_id)` unique 하나만
- 장점: 2와 3을 인덱스 하나로 해결한다.
- 단점: 1이 테이블 전체를 훑고 정렬도 따로 한다.

### C. `(user_id, room_id)` unique + `(room_id)` 인덱스
- 장점: 1, 2, 3 모두 인덱스를 쓴다.
- 단점: 참여와 나가기 때 인덱스 두 개를 갱신하고, 저장 공간을 더 쓴다.

## 결정

C를 선택한다.

## 이유 (오너 작성)

처음 답:

> A 안을 채택할게. C안은 인덱스를 두 개 갱신하고 저장 공간도 두 배로 쓰는데
> 사실상 2, 3보다는 1은 앱을 열때마다 호출하니 더 빈번하게 일어날 것이라서 A 안을 채택할게

되물음: 3단계에서 2는 메시지마다 호출된다. 사용자가 앱을 한 번 열고 메시지를 여러 번 주고받으면 1과 2 중 어느 쪽이 더 자주 호출되나?

> 2가 더 자주 호출되겠네... 메시지를 보낼 때마다 발송 대상을 찾기 위해서 2를 호출한다는 생각을 하지 못했어.

C의 비용이 코드 한 줄과 참여자 테이블 쓰기(참여, 나가기)에만 든다는 설명을 들은 뒤:

> C를 유지할게. 앞선 1,2,3에 대해서 인덱스를 사용하도록 하는 대신 저장 공간 부하를 감수할게

## 결과

- `ChatRoomMember`에 `(user_id, room_id)` unique 제약과 `(room_id)` 인덱스를 선언하고, `ddl-auto`로 만든다.
- 구현한 뒤 1과 2가 실제로 인덱스를 쓰는지 `EXPLAIN`으로 확인한다(Issue #7 작업 목록). 데이터가 적으면 PostgreSQL이 인덱스 대신 전체 스캔을 고를 수 있으니, 확인할 때는 데이터를 충분히 넣는다.

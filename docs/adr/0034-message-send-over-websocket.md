# 0034. 메시지 보내는 경로: WebSocket 프레임으로 보낸다

- 상태: 채택
- 날짜: 2026-11-22
- 로드맵 단계: 3
- Issue: #9

## 맥락

메시지를 받는 쪽은 WebSocket으로 정해졌다(ADR 0030). 이번에는 앱이 메시지를 보내는 경로를 정한다.

## 선택지

### A. WebSocket으로 보낸다
이미 열린 연결로 `{"type":"SEND","roomId":…,"content":…}` 프레임을 보낸다.
- 장점: 요청마다 HTTP 연결과 헤더를 붙이지 않는다. 보내기와 받기가 연결 하나로 끝난다.
- 단점: HTTP처럼 요청과 응답을 짝지어 주는 구조가 없다. 성공/실패 응답(ack), 요청 id, 에러 프레임, 검증 실패 처리를 직접 설계해야 한다. `@Valid`, `GlobalExceptionHandler` 같은 REST 구조를 그대로 쓸 수 없다.

### B. REST로 보내고 WebSocket으로는 받기만 한다
`POST /rooms/{id}/messages`로 저장하면, 서버가 방 참여자의 연결로 밀어 준다.
- 장점: 응답 코드, 검증, 에러 형식, JWT 필터, 테스트 방식을 그대로 쓴다. 보낸 사람이 HTTP 응답으로 결과를 바로 안다. WebSocket이 끊겨 있어도 보낼 수 있다.
- 단점: 메시지마다 HTTP 요청 비용이 든다. 보낸 사람에게 결과가 두 번 온다(HTTP 응답, WebSocket 수신). 연결 관리로 배울 거리가 받기에 한정된다.

## 결정

A를 선택한다.

## 이유 (오너 작성)

> 메시지의 발송 횟수가 많아지면 REST로 보낼 때의 부하가 높아질 것 같아. 공부 목적의 프로젝트이므로 성공/실패 응답, 에러 프레임, 검증 실패 처리를 직접 설계하는 WebSocket 방식을 채택할게.

## 결과

- `shared`의 프로토콜에 클라이언트 → 서버 `SEND` 프레임을 둔다. 보낸 사람에게 돌려줄 성공 응답 프레임과 에러 프레임도 정의한다.
- 성공/실패 응답을 어느 `SEND`에 대한 것인지 알 수 있도록, 클라이언트가 붙이는 요청 id를 프레임에 둔다. 세부 형식은 저장/전달 순서와 함께 정한다.
- 내용 길이, 방 참여 여부(나간 사람 제외, ADR 0026) 같은 검증은 핸들러에서 직접 한다. 실패하면 HTTP 상태 코드 대신 기존 `ErrorCode`를 담은 에러 프레임을 보낸다. 연결은 끊지 않는다.
- 메시지 이력 조회는 지금처럼 REST(커서 페이지네이션)로 한다.

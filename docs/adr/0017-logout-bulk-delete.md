# 0017. 로그아웃 삭제: 벌크 DELETE

- 상태: 채택
- 날짜: 2026-11-09
- 로드맵 단계: 1
- Issue: #3

## 맥락

로그아웃은 `(user_id, device_id)` 행을 지운다(ADR 0016). 처음에는 derived delete(`deleteByUserIdAndDeviceId`)로 구현했다. derived delete는 엔티티를 select로 불러온 뒤 커밋 시점에 `delete ... where id=?`를 보낸다.

같은 기기 로그아웃을 동시에 2번 보내는 실험을 10회 했더니 9회에서 한쪽이 500을 받았다. 두 요청이 모두 행을 불러오고, 늦은 쪽의 DELETE가 0행을 지우자 Hibernate가 `StaleObjectStateException`(1행을 기대했는데 0행)을 던졌다.

## 선택지

### A. 벌크 DELETE (`@Modifying @Query`)
- 장점: 쿼리 하나로 끝난다. 0행이면 예외 없이 정상 종료한다. 실제 삭제 수를 돌려준다.
- 단점: 엔티티 생명주기(`cascade`, `orphanRemoval`, `@PreRemove`)를 거치지 않는다. 영속성 컨텍스트를 우회한다. JPQL을 직접 쓴다.

### B. derived delete 유지 + 예외를 잡아 성공 처리
- 장점: 엔티티 생명주기를 유지한다.
- 단점: 쿼리가 2개다. 예외가 커밋 시점에 트랜잭션 프록시 밖에서 터지므로 서비스 바깥에서 잡아야 한다. 같은 예외의 다른 원인까지 성공으로 처리할 위험이 있다.

### C. 비관적 락 (`@Lock(PESSIMISTIC_WRITE)`)
- 장점: 두 번째 요청이 select에서 기다렸다가 행이 없음을 확인한다.
- 단점: 쿼리가 2개이고 잠금을 유지하는 시간이 가장 길다.

## 결정

A를 선택한다.

## 이유 (오너 작성)

> 1번 벌크 DELETE로 할게. 나중에 엔티티 생명주기 처리가 필요해지면 2번을 고려할게

## 결과

- 동시 로그아웃은 한쪽이 1행, 다른 쪽이 0행을 지우고 둘 다 204로 끝난다(실험: 10회 모두 204).
- 지금은 `RefreshToken`에 자식 엔티티도 삭제 콜백도 없어서 생명주기를 우회해도 잃는 것이 없다.
- 다시 검토할 조건: 로드맵 5단계에서 FCM 토큰을 `RefreshToken`의 자식 엔티티로 두거나, 삭제할 때 콜백(`@PreRemove`)으로 외부 처리를 하게 되는 경우.

## 나중에 알게 된 것

- (2026-11-09) `@Transactional`은 다른 요청을 막는 잠금이 아니다. 동시 실험에서 두 트랜잭션은 동시에 select했고, 늦은 쪽을 기다리게 한 것은 PostgreSQL이 DELETE 대상 행에 건 행 잠금이었다.
- (2026-11-09) derived delete의 반환값은 커밋 전에 "불러온 개수"라서, 실제로는 0행이 지워졌어도 로그에는 `deleted=1`로 찍혔다.

# 0005. 인증: JWT + Refresh Token

- 상태: 채택
- 날짜: 2026-11-07
- 로드맵 단계: 1
- Issue: #3

## 맥락

모바일 앱이 보내는 요청이 어떤 사용자의 것인지 서버가 식별해야 한다. 서버는 7단계에서 여러 대로 늘어날 예정이다.

## 선택지

### A. 세션
- 장점: 구현이 단순하다(Spring Session). 강제 로그아웃이 즉시 된다.
- 단점: 매 요청마다 세션 저장소를 조회한다. 서버가 여러 대면 모든 서버가 세션 저장소를 공유해야 한다.

### B. JWT + Refresh Token
- 장점: 일반 요청은 서명만 검증하고 저장소를 조회하지 않는다. Access Token은 어느 서버에서든 검증할 수 있다.
- 단점: 발급, 재발급, 교체, 탈취 감지를 직접 설계해야 한다. 강제 로그아웃이 Access Token 수명만큼 늦다.

## 결정

B. JWT(Access Token) + Refresh Token을 사용한다.

## 이유 (오너 작성)

> 세션 저장소를 모든 서버가 공유해야 하는 부담을 피하고, 사용자 인증에 필요한 정보를 토큰에 담기 위해

## 결과

- 강제 로그아웃을 하려면 **서버가 Refresh Token을 저장**하고, 무효화할 때 저장소에서 지워야 한다. JWT도 서버 저장이 완전히 없어지는 것은 아니고, 저장소를 조회하는 빈도가 줄어드는 것이다.
- 토큰은 서명만 되어 있고 암호화되어 있지 않다. 사용자 ID와 권한 정도만 담고 개인정보는 넣지 않는다.
- 3단계(WebSocket)에서 연결 중에 Access Token이 만료되는 경우를 따로 정해야 한다.

# 0022. 1:1 방 중복 생성 방지: 조회 후 생성 + 사용자 행 잠금

- 상태: 채택
- 날짜: 2026-11-10
- 로드맵 단계: 2
- Issue: #7

## 맥락

같은 두 사람 사이에는 `DIRECT` 방이 하나만 있어야 한다(ADR 0019). 두 사람이 동시에 서로에게 1:1 방을 만들어도 마찬가지다. 참여자는 `chat_room_members`에 있다(ADR 0020).

## 선택지

### A. 방에 두 사람의 조합을 저장하고 unique 제약
`chat_rooms`에 정렬한 두 id(`direct_user_low`, `direct_user_high`)를 저장하고 일반 unique 제약을 건다. 그룹 방은 두 컬럼이 `NULL`이라 제약에 걸리지 않는다.
- 장점: DB가 중복을 보장한다. 기존 방 조회가 단순하다. 같은 조합이 실제로 동시에 생성될 때만 기다린다.
- 단점: 참여자 정보가 두 곳에 저장된다(비정규화). unique 위반 뒤에는 그 트랜잭션을 더 쓸 수 없어서 기존 방 재조회를 어디서 할지 신경 써야 한다.

### B. 조회 후 생성
두 사람이 함께 속한 `DIRECT` 방을 멤버 테이블에서 찾고, 없을 때만 만든다.
- 장점: 스키마를 추가하지 않는다. 참여자 정보가 한 곳에만 있다.
- 단점: 동시 요청이면 방이 두 개 생긴다. 멤버 테이블을 자기 자신과 조인해야 한다.

### C. B + 사용자 행 잠금
조회 전에 두 사용자의 `users` 행을 id 오름차순으로 `SELECT ... FOR UPDATE` 한다.
- 장점: 스키마를 추가하지 않고 동시 요청을 직렬화한다.
- 단점: 같은 사용자가 관련된 다른 1:1 방 생성과 그 사용자 행의 수정까지 기다린다. 잠금 순서를 지키지 않으면 데드락이 생긴다.

### D. B + 조합 단위 잠금 (PostgreSQL advisory lock)
- 장점: 같은 두 사람 조합만 기다린다.
- 단점: PostgreSQL 전용 함수를 네이티브 쿼리로 호출해야 한다.

## 결정

C를 선택한다.

## 이유 (오너 작성)

> A 방안의 비정규화 위험과 PostgreSQL에만 있는 기능인 부분 인덱스를 사용하지 않기 위해
> B를 사용하면서도 동시에 방을 생성할 때 중복 생성을 막을 수 있도록 C 안을 채택할게

되물음: 사용자 3이 7, 9와의 1:1 방을 동시에 만들면 어떤 행이 잠기고 어떻게 동작하나? 감수할 수 있나? 이어서 A에 부분 인덱스가 필요하다는 AI 설명이 틀렸음을 정정하고(일반 unique 제약으로 충분), D를 추가로 제시했다.

> C를 유지할게. 학습용인만큼 PostgreSQL 전용 기능을 최소화하고 데이터 비정규화를 방지하기 위함이야. 실제로 트래픽이 높지 않기 때문에 다른 유저 정보를 변경하는 API가 동시에 호출되더라도 기다릴만할 것 같아

## 결과

- 1:1 방 생성은 한 트랜잭션 안에서 "두 사용자 행을 id 오름차순으로 잠금 → 기존 방 조회 → 없으면 생성" 순서로 처리한다.
- 같은 사용자가 관련된 1:1 방 생성은 서로 기다린다. 사용자 행을 수정하는 작업도 그동안 기다린다.
- 잠금 순서가 어긋나면 데드락이 생겨 한쪽 요청이 실패한다. 잠금 순서는 한 곳에서만 정한다.

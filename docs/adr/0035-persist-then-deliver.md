# 0035. 저장과 전달의 순서: 커밋 후 전달

- 상태: 채택
- 날짜: 2026-11-22
- 로드맵 단계: 3
- Issue: #9

## 맥락

`SEND` 프레임(ADR 0034)을 받으면 서버는 DB에 저장하고, 방 참여자들의 연결로 전달한다. 두 작업의 순서와, 트랜잭션과의 관계를 정한다.

## 선택지

### A. 커밋 후 전달
저장 → 커밋 → 보낸 사람에게 성공 응답 → 참여자에게 전달.
- 장점: 받은 메시지는 모두 DB에 있다. 전달 프레임에 DB가 매긴 id를 실을 수 있다.
- 단점: 받는 사람이 보기까지 DB 쓰기 시간이 더해진다. 커밋 직후 서버가 죽으면 저장됐지만 아무도 받지 못한 메시지가 생긴다(재연결 복구로 메운다).

### B. 전달 먼저, 저장은 뒤에
참여자에게 전달 → 저장(비동기 등).
- 장점: 받는 사람이 가장 빨리 본다.
- 단점: 저장이 실패하면 받는 사람은 봤는데 DB에는 없는 유령 메시지가 생긴다. 전달할 때는 아직 DB id가 없어서 순서와 복구 기준을 따로 만들어야 한다.

### C. 트랜잭션 안에서 전달
`@Transactional` 메서드 안에서 저장 → 전달 → 메서드가 끝날 때 커밋.
- 장점: 메서드 하나로 끝나서 코드가 가장 단순하다.
- 단점: 전달한 뒤 커밋이 실패하거나 롤백되면 B처럼 유령 메시지가 생긴다. 느린 연결로 보내는 동안 DB 커넥션과 트랜잭션을 붙잡고 있다.

## 결정

A를 선택한다.

## 이유 (오너 작성)

> A안을 선택할게. 받은 메시지가 모두 DB에 있음을 보장하기 위해서야

## 결과

- 메시지 저장은 트랜잭션 하나로 끝낸다. 성공 응답과 전달은 트랜잭션 밖, 커밋이 끝난 뒤에 한다. 전달 코드를 `@Transactional` 메서드 안에 두지 않는다.
- 전달 프레임에는 DB가 매긴 메시지 id를 싣는다. 이 id를 순서와 재연결 복구의 기준으로 쓸 수 있는지는 순서 보장 결정에서 정한다.
- 저장에 실패하면 보낸 사람에게 에러 프레임을 보내고, 아무에게도 전달하지 않는다.
- 커밋은 됐지만 전달하지 못한 메시지는 재연결 복구로 메운다. 전달 실패를 어떻게 다룰지는 따로 정한다.

# 0029. 내 채팅방 목록은 참여자 목록 대신 요약 정보를 내려준다

- 상태: 채택
- 날짜: 2026-11-22
- 로드맵 단계: 2
- Issue: #7

## 맥락

내 채팅방 목록은 방 id 내림차순(ADR 0023)과 불투명 커서(ADR 0024)로 페이지를 나눈다. 1:1 방은 `name`이 null이라서, 앱이 목록에 상대 닉네임을 보여 주려면 방마다 참여자 정보가 필요하다.

참여 응답과 같은 `RoomResponse`(참여자 목록 포함)를 목록 항목으로 쓰고 방마다 `findActiveMembers`(ADR 0028)를 호출하면, 방 20개짜리 페이지에서 쿼리가 21번 나간다. 참여자마다 생기던 N+1(ADR 0028)이 방 단위로 다시 생기는 것이다.

`@OneToMany` 컬렉션을 fetch join으로 한 번에 가져오는 방법은 처음부터 제외했다. 방 하나가 참여자 수만큼의 행으로 부풀려져 DB에서 `limit`을 걸 수 없고, Hibernate가 모든 행을 메모리로 가져온 뒤 페이지를 자르기 때문이다.

## 선택지

### A. 방마다 참여자 조회
- 장점: 코드가 가장 단순하고 기존 쿼리를 다시 쓴다.
- 단점: 쿼리 수가 페이지 크기 + 1이다(`size=50`이면 51번).

### B. 페이지의 방 id로 `IN` 조회 한 번
- 장점: 페이지 크기와 관계없이 쿼리가 2번이다. 직접 쿼리를 쓰면 쿼리가 코드에 드러나고, Hibernate 배치 페치(`default_batch_fetch_size`)로도 같은 SQL을 만들 수 있다.
- 단점: 쿼리 하나와 메모리에서 방별로 묶는 코드가 는다. 배치 페치는 `ChatRoom.members` 컬렉션을 거치는데, 이 컬렉션은 나간 사람까지 담아서 응답에 쓰지 않기로 했다(ADR 0028).

### C. 목록에는 참여자 목록을 담지 않는다
목록 항목을 요약 DTO(id, 종류, 표시 이름)로 바꾸고, 1:1 방은 상대 닉네임만 조회해서 담는다.
- 장점: 목록 한 줄에 필요한 것만 내려준다. 참여자가 많은 그룹 방이 있어도 응답이 가볍다. 쿼리는 1~2번이다.
- 단점: `shared`에 DTO를 새로 만든다. 참여자 목록이 필요하면 방 상세 API가 따로 필요하다.

## 결정

C를 선택한다.

## 이유 (오너 작성)

> 메신저 목록 화면에 사용하게 되면 참여 사용자 목록을 전부 다룰 필요가 없기 때문에
> C로 갈게. 응답을 가볍게 만들고 방마다 조회했을 때 생기는 N+1 쿼리 문제를 해결하기 위함이야

## 결과

- `shared`에 `RoomSummaryResponse(id, type, title)`를 추가한다. `title`은 그룹 방이면 방 이름, 1:1 방이면 상대 닉네임이다.
- 내 방 목록 API는 `CursorPage<RoomSummaryResponse>`를 내려준다.
- 쿼리는 두 번이다. 내 방 `size + 1`개를 가져오는 쿼리와, 그중 1:1 방들의 상대 닉네임을 `IN`으로 한 번에 가져오는 쿼리다. 1:1 방이 없으면 두 번째 쿼리는 실행하지 않는다.
- 상대가 1:1 방에서 나갔어도 그 방은 여전히 "그 사람과의 방"이므로, 상대 닉네임 조회는 `left_at`을 보지 않는다.
- 3단계에서 마지막 메시지와 안 읽은 수(4단계)를 요약 DTO에 추가한다.

# 0001. 브랜치 전략: Git Flow

- 상태: 채택
- 날짜: 2026-11-07
- 로드맵 단계: 0 (프로젝트 세팅)

## 맥락

모노레포 하나에 배포 리듬이 다른 두 소프트웨어가 함께 있다.

- 서버: 언제든 다시 배포할 수 있고, 롤백도 몇 분이면 된다.
- 앱: 스토어 심사를 거쳐야 하고, 한번 배포하면 되돌릴 수 없다.

CI/CD로 서버를 배포하는 경험을 하는 것도 목표다.

## 선택지

### A. Git Flow (`main`, `develop`, `feature/*`, `release/*`, `hotfix/*`)
- 장점: 버전 단위로 출시하기 좋다. 모바일에서 익숙한 방식이다.
- 단점: 단계가 많아서 변경이 배포되기까지 오래 걸린다. 혼자 하는 프로젝트에는 다소 무겁다.

### B. GitHub Flow (`main` + `feature/*`, 머지하면 바로 배포)
- 장점: 단순하다. 머지와 배포가 바로 이어진다.
- 단점: `main`이 항상 배포 가능해야 한다. 출시 버전을 관리하는 구조가 없다.

### C. Trunk-based + 태그 릴리스
- 장점: 서버(머지할 때 배포)와 앱(태그를 달 때 릴리스)의 리듬을 트리거로 분리한다.
- 단점: 개념이 가장 많다. Feature Flag 같은 장치가 필요하다.

## 결정

A. Git Flow를 사용한다.

## 이유 (오너 작성)

> main 브랜치에서 병합되었을 때 (서버가 배포된다)

## 결과

- 서버 배포 트리거: `main`에 머지될 때 (`server/**`, `shared/**` 경로가 바뀐 경우에만)
- 일반 변경 경로: `feature/*` → `develop` → `release/*` → `main` → 배포
- 긴급 수정 경로: `hotfix/*` → `main` (배포) → `develop`에 역머지
- `develop`: PR마다 CI(빌드와 테스트)만 돌리고, 배포는 하지 않는다.

## 아직 정하지 않은 것

- 앱 릴리스 트리거: `main` 머지 시 / 태그 시 / 수동 (앱을 스토어에 올리는 단계에서 결정)
- 스테이징 서버: `develop` 또는 `release/*`를 별도 환경에 배포할지 (로드맵 8단계에서 결정)

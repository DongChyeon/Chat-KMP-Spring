# 0014. 재발급 실패 응답: 전용 에러 코드 하나

- 상태: 채택
- 날짜: 2026-11-09
- 로드맵 단계: 1
- Issue: #3

## 맥락

토큰 재발급 API는 Refresh Token을 받아 새 Access Token을 발급한다. 재발급이 실패하는 원인은 세 가지다.

- Refresh JWT 만료
- DB 허용 목록에 없음 (로그아웃했거나 같은 기기에서 다시 로그인해 폐기됨)
- 위조, 형식 오류, 종류가 다른 토큰(Access Token)

앱은 보호 API에서 `TOKEN_EXPIRED`를 받으면 재발급을 시도하고, `INVALID_TOKEN`을 받으면 로그아웃한다(ADR 0013). 재발급이 실패했을 때 어떤 코드로 응답할지 정해야 한다.

## 선택지

### A. 기존 코드 재사용 (`TOKEN_EXPIRED` / `INVALID_TOKEN`)
- 장점: 코드 수가 늘지 않는다.
- 단점: `TOKEN_EXPIRED`가 "재발급하라"와 "다시 로그인하라" 두 뜻을 갖는다. 앱이 어느 API에서 받았는지로 구분해야 하고, 구분하지 않으면 재발급을 무한 반복한다.

### B. 재발급 전용 코드 하나 (`REFRESH_FAILED`)
- 장점: 앱은 "받으면 로그인 화면" 하나만 처리한다. 요청한 쪽에 토큰 상태가 드러나지 않는다.
- 단점: 서버 로그 없이는 실패 원인을 구분할 수 없다. 사용자 안내 문구도 하나뿐이다.

### C. 원인별로 나눔 (`REFRESH_TOKEN_EXPIRED` / `REFRESH_TOKEN_REVOKED` / `INVALID_TOKEN`)
- 장점: "다른 기기에서 로그아웃되었습니다" 같은 안내가 가능하고 디버깅이 쉽다.
- 단점: 앱의 분기와 코드 수가 늘어난다. 요청한 쪽에 토큰 상태(폐기됨)가 드러난다.

## 결정

B를 선택한다.

## 이유 (오너 작성)

> 토큰 상태 정보를 앱 사용자에게 노출하지 않으면서, 재발급이랑 다시 로그인하라를 API가 아닌 에러코드만으로 판단할 수 있기 때문이야.

## 결과

- 재발급 실패는 원인과 관계없이 401 `REFRESH_FAILED`로 응답한다. 원인은 서버 로그에만 남긴다.
- 재발급 API는 `permitAll`이다. Refresh Token은 `Authorization` 헤더가 아닌 요청 본문으로 받는다.
- 앱은 재발급 요청에 `Authorization` 헤더를 붙이지 않아야 한다. 만료된 Access Token을 붙이면 인증 필터가 먼저 `TOKEN_EXPIRED`를 돌려준다(ADR 0013).

# 0018. 테스트 DB: Testcontainers

- 상태: 채택
- 날짜: 2026-11-09
- 로드맵 단계: 1
- Issue: #3

## 맥락

서버 테스트(회원가입, 로그인, 재발급, 로그아웃, 동시성)를 어떤 DB에서 돌릴지 정해야 한다. 동시 가입 레이스와 동시 로그아웃은 PostgreSQL의 unique 제약과 행 잠금에 기대고 있다. CI는 로드맵 8단계에서 붙인다.

## 선택지

### A. Testcontainers
- 장점: 테스트마다 PostgreSQL 18 컨테이너를 띄워 운영과 같은 DB에서 검증한다. 개발 DB와 격리된다. CI에서도 Docker만 있으면 된다.
- 단점: 의존성이 늘고, 컨테이너 기동으로 테스트 시작이 몇 초 느려진다. Docker가 꺼져 있으면 테스트가 돌지 않는다.

### B. H2 (인메모리)
- 장점: Docker 없이 가장 빠르고 설정이 간단하다.
- 단점: PostgreSQL과 SQL 문법, 제약 위반 에러, 잠금·격리 동작이 달라서 테스트 결과를 믿기 어렵다.

### C. docker compose DB 재사용
- 장점: 새 의존성이 없고 실제 DB와 같다.
- 단점: 테스트 전에 DB를 수동으로 띄워야 하고, 남은 데이터가 테스트에 영향을 준다. CI에서 compose를 따로 실행해야 한다.

## 결정

A를 선택한다.

## 이유 (오너 작성)

> H2 인메모리 데이터베이스는 현재 PostreSQL과 환경 차이가 나서 환경 문제로 테스트가 실패하는 경우가 있고
> 3번은 매번 테스트 전에 수동으로 DB를 띄우고, 남은 데이터로부터 영향을 받지 않으려면 남은 데이터를 삭제해야하기 때문이야

## 결과

- 테스트 이미지는 `docker-compose.yml`과 같은 `postgres:18-alpine`을 쓴다.
- Spring Boot의 `@ServiceConnection`으로 컨테이너 접속 정보를 datasource에 연결한다. `application.properties`의 DB 설정은 테스트에서 덮어쓴다.
- 테스트를 돌리려면 Docker가 실행 중이어야 한다.

## 나중에 알게 된 것

- (2026-11-09) 테스트에 `@Transactional`(끝나면 롤백)을 붙이면 테스트가 만든 행은 커밋 전이라 다른 스레드에서 보이지 않는다. 그 상태로 동시 로그아웃을 돌리면 두 스레드 모두 0행을 지우고 통과한다. 실제로는 500이 나던 derived delete도 통과했다(거짓 통과). 동시성 테스트는 롤백 대신 테스트마다 다른 데이터를 쓴다.

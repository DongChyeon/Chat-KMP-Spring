# 0010. Refresh Token 저장: PostgreSQL 허용 목록, 교체하지 않음

- 상태: 채택
- 날짜: 2026-11-07
- 로드맵 단계: 1
- Issue: #3

## 맥락

강제 로그아웃을 하려면 서버가 Refresh Token을 저장해야 한다(ADR 0005). 어디에 저장할지, 재발급할 때 Refresh Token도 교체할지 정해야 한다.

## 선택지

### 저장 위치
- **PostgreSQL 테이블**: 이미 있는 DB에 테이블을 추가한다. 만료된 행을 주기적으로 지워야 한다.
- **Redis**: TTL로 만료가 자동 처리되고 더 빠르다. 새 인프라를 추가해야 하고, 설정에 따라 약간의 데이터 유실을 감수해야 한다.

### 저장 방식
- **허용 목록 (유효한 토큰을 저장)**: 데이터를 잃으면 사용자가 다시 로그인한다. 불편하지만 안전하게 실패한다.
- **차단 목록 (무효화한 토큰을 저장)**: 데이터를 잃으면 차단한 토큰이 다시 유효해진다.

### 교체(rotation)
- **교체하지 않음**: 같은 Refresh Token을 만료까지 쓴다. 단순하지만, 탈취되면 강제 로그아웃 전까지 악용될 수 있다.
- **재발급할 때마다 교체**: 탈취를 감지할 수 있다. 하지만 앱이 동시에 재발급을 두 번 요청하면 정상 사용자가 로그아웃될 수 있어 서버와 앱 양쪽에 동기화 처리가 필요하다.

## 결정

- PostgreSQL 테이블에 **허용 목록** 방식으로 저장한다.
- 재발급할 때 Refresh Token은 **교체하지 않는다.**

## 이유 (오너 작성)

> 저장 위치: 일단은 PostgreSQL을 사용하다가 나중에 Redis를 도입해야한다면, 그때 도입해서 속도 차이를 체감하도록 할게

> 저장 방식: 유효한 토큰 목록 사용

> 교체: 둘 다 401을 받는다면 재발급 요청 로직이 클라이언트단에서 판단하기 복잡해져. 그리고 그정도의 보안을 신경쓰지 않아도 될 것 같아

## 결과

- Refresh Token은 원문 대신 해시로 저장한다. DB가 유출돼도 저장된 값으로 바로 재발급받을 수 없게 한다.
- 만료된 행을 주기적으로 지우는 작업이 필요하다.
- 사용자당 하나만 저장할지, 기기별로 저장할지는 테이블을 설계할 때 정한다.
- Refresh Token이 탈취되면 강제 로그아웃 전까지 최대 30일 동안 악용될 수 있다. 감수하기로 한 위험이다.

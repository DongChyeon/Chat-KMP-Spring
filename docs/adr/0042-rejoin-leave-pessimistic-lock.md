# 0042. 재참여와 퇴장을 정확히 한 번: 참여 행 비관적 락

- 상태: 채택
- 날짜: 2026-11-23
- 로드맵 단계: 3
- Issue: #9
- 대체: ADR 0027의 축 2 (축 1, 이미 참여 중이면 409는 유지)

## 맥락

ADR 0041에 따라 입장/퇴장을 시스템 메시지로 저장한다. ADR 0027은 재참여 전이에 동시성 제어를 두지 않아서, 동시 재참여 요청이 여러 번 200을 받을 수 있다. 이 상태에서 입장 메시지를 붙이면 여러 줄이 저장되어 영구히 남는다.

퇴장도 같다. 지금은 "참여 중인 행을 찾음 → `leave()`" 순서라, 동시 요청 두 개가 둘 다 참여 중인 행을 보고 204를 받는다. 그러면 퇴장 메시지도 두 줄이 된다.

처음 참여(INSERT)는 `(user_id, room_id)` unique 제약이 두 번째부터 거부하고 그 트랜잭션이 롤백되므로 문제가 없다.

## 선택지

### B. 비관적 락
참여 행을 `SELECT … FOR UPDATE`로 읽는다. 두 번째 요청은 첫 번째가 커밋할 때까지 기다렸다가, 바뀐 `left_at`을 보고 409/404로 간다.
- 장점: 지금 코드 흐름(찾고 → 분기 → 변경)을 유지하고 쿼리만 바꾼다. ADR 0022에서 써 본 방식이다.
- 단점: 같은 사람이 같은 방에 동시에 보낸 요청끼리 줄을 서며 커넥션을 붙잡는다.

### C. 낙관적 락
참여 행에 `@Version`을 두고, 커밋할 때 버전이 바뀌었으면 예외를 던진다.
- 장점: 기다리지 않는다.
- 단점: 컬럼과 마이그레이션이 늘어난다. 충돌 예외가 커밋 시점에 나서 트랜잭션 밖에서 응답으로 바꿔야 한다.

### D. 조건부 UPDATE
`update … set left_at = null where id = ? and left_at is not null`처럼 조건을 걸고, 바뀐 행이 0이면 409/404로 처리한다.
- 장점: 쿼리 하나로 원자적이다. 기다림도 컬럼 추가도 없다.
- 단점: `@Modifying` 쿼리를 직접 써야 한다. 엔티티 메서드를 거치지 않아 영속성 컨텍스트와 DB 값이 어긋날 수 있다.

## 결정

B를 선택한다.

## 이유 (오너 작성)

> 같은 사람이 같은 방에 동시에 요청을 보낼 일은 실질적으로 적으니까 B를 선택할게

## 결과

- 재참여(`join`)와 퇴장(`leave`)은 참여 행을 비관적 쓰기 락으로 읽은 뒤 분기한다. 락을 거는 범위는 `(room_id, user_id)` 한 행이다.
- 동시 재참여는 200 하나와 나머지 409, 동시 퇴장은 204 하나와 나머지 404가 된다. 입장/퇴장 메시지는 성공한 한 번에만 저장된다.
- ADR 0027의 테스트(200이 여러 개일 수 있음)는 "200이 정확히 하나"로 바꾼다. 퇴장 동시성 테스트를 추가한다.
- 처음 참여 경로(행이 없을 때)는 잠글 행이 없으므로 지금처럼 unique 제약에 맡긴다.
